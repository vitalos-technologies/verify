# Implementation decisions (repository)

Recorded per 02_decisions_and_assumptions.md: date, decision, alternatives, impact. All dated 2026-11-10.

| ID | Decision | Alternatives considered | Impact / revisit |
|---|---|---|---|
| IMP-01 | Repository is `vitalos-technologies/verify` (owner-created) rather than the proposed `vitalos-verify` (ADR-07). | Create new repo | None. |
| IMP-02 | API and worker ship from one Python package (`services/api`, entrypoints `vv-api`, `vv-worker`), deployed as separate processes. | Separate `services/worker` package | Matches ADR-10 modular monolith; split when measured need appears. |
| IMP-03 | Prototype queue is PostgreSQL tables (`provider_events`, `outbox`, `webhook_deliveries`) polled by the worker. | SQS (05_architecture) | No cloud dependency before M02-T04. Swap transport to SQS when infra exists; outbox semantics unchanged. |
| IMP-04 | Synthetic country `ZZ` (ISO 3166 user-assigned) is the only enabled coverage, routed to the DummyProvider and refused in staging/production. | Enable GB entries against dummy | Prevents any implied real-document support. |
| IMP-05 | Policy rule order: technical error → high-risk indicator → capture quality → missing evidence → expiry/support → mandatory pass. | Spec order (missing evidence before high-risk) | A poor capture legitimately leaves downstream checks `not_run`; suspected attack must not be masked as "missing". Security floor unchanged: nothing approves unless every mandatory check passes. |
| IMP-06 | Pilot routes `fail`/`inconclusive` face match, liveness and authenticity to `review_required`; automated `declined` only for an expired document after retries. | Auto-decline on failures | Conservative (07 §Example pilot policy, 10 §Meaningful review). Revisit with assurance owner. |
| IMP-07 | `/console/dev-login` stands in for OIDC sign-in in development/test/ci only. | Build Cognito integration now | IdP not selected (M01). Not mounted outside non-production. |
| IMP-08 | Row-level security enabled (not forced); runtime roles `vv_app`/`vv_worker` are non-owners without BYPASSRLS. Pre-tenant lookups use five narrow SECURITY DEFINER functions. | FORCE RLS + owner-run lookups | Owner/migration role can bypass RLS; restrict its use to migrations. |
| IMP-09 | Provider callbacks carry no result: the worker always fetches the authoritative observation. | Trust signed callback payload | Signed-but-stale or misrouted callbacks cannot approve (AT-06). |
| IMP-10 | Prices in code (`session_price_minor=250`) are the 16_pricing hypothesis, labelled as such in policy cost previews. | — | Not an approved price; replace when M06 pricing is decided. |
| IMP-11 | `POST /v1/deletions` `subject_id` accepts the internal subject ID or the customer's `external_reference`. | Internal ID only | Customers never receive internal subject IDs in the current contract; revisit when contract v1.1 is drafted. |
| IMP-12 | Deletion redacts identifiers (subject/session references, contact hashes, raw provider bodies) and keeps checks/decisions/audit, which hold no direct identifiers. | Hard-delete sessions | Keeps the outcome reproducible for the customer while removing linkage. Controller must ratify. |
| IMP-13 | `processing`/`error` sessions may expire after their deadline when no decision exists. | Leave stuck forever | Releases the reservation; spec 07 only listed created/in_progress/action_required. |
| IMP-14 | Public contract 1.1.0 (additive): `Session.decision` summary and optional `ReviewDecision.reviewer_reference`. | Reason codes in webhooks only | Alternative-method approvals must be distinguishable (07, 10). Backward compatible. |
| IMP-15 | Second-review rule enforced for console reviews and appeals; API-key decisions are not second-reviewed, and only owner/administrator roles can mint `decisions:write` keys. | Block API alternative-method approvals | Customers with their own review UI own that control; revisit before managed review (M14). |
| IMP-16 | API keys are tenant credentials and are not revoked when their creating member is revoked. | Auto-revoke | Avoids breaking integrations on staff changes; owners rotate keys explicitly. |
| IMP-17 | Applicant UI copy is minimal: short heading, at most one short line per screen (owner instruction). | Explanatory copy | Final notice wording still needs controller approval. |
| IMP-18 | Tombstone log stored outside database backups (separate S3 prefix; local dir in dev) and replayed before serving after any restore. | Tombstones only in the DB | A backup older than a deletion has no tombstone row (verifier D-A). |
| IMP-19 | Platform staff (admin/operations) use a separate sign-in and see metadata only through definer views. | Superuser DB access | Matches 10_review §Support access; no subject data or evidence in platform screens. |
| OWN-01 | Owner approved (10 Nov 2026): Workforce PR, ADR-022 single platform Verify account, 30-day evidence retention, 35-day backup retention, "Book a demo" → vitalos.co.uk. | — | Retention is the Vitalos default; each customer (controller) still ratifies it in its DPA before real data. |
| IMP-20 | Console sign-in = Google or email magic link, then an authenticator app (TOTP). Google tokens rarely assert MFA, and a magic link is one factor, so the app code is the second factor. Google identities map to members by verified email only. | Google-only, passkeys | Owner choice (10 Nov 2026). Passkeys can be added later as a second factor. |
